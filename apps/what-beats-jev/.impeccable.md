# Design context: What Beats Jev

Status: The user approved the [screen-design brief](./docs/design-brief.md) and defaults, explicitly reaffirming Fluid Functionalism.

## Design Context

### Users

Public casual players. The initial experience is completely anonymous, with no required identity or account and no leaderboard. Players propose what beats the current challenge using free-form text up to 240 visible Unicode characters, aiming to build the longest accepted chain before losing. Runs are untimed. Desktop, mobile, and any viewport must receive first-class responsive support.

### Brand personality

Whimsical, playful, and toy-like. The recommended bright direction, expressive typography, and tactile controls were accepted. The final name and more specific voice are still open.

### Aesthetic direction

Use actual Fluid Functionalism registry components for the implemented UI, themed as the approved bright, light, tin-toy logic game. The game owns a standalone Next.js app at `apps/what-beats-jev`. Use the approved palette and Sour Gummy/Figtree typography from the design brief. Design work belongs on Doop canvas `oJGrvv12x1`; its self-contained HTML prototypes demonstrate the component anatomy and motion, not an installed React app.

Sushiro's minimalist queue-map styling belongs to a separate product. Jev produces structured decisions rather than generated prose, so screen concepts cannot depend on improvised explanations.

Answers may describe potentially anything, so concepts must accommodate text rather than assume every challenge has a known icon or illustration. Jev alone decides whether a proposed relationship wins.

A phrase already in the current chain cannot be reused during that run, including the starting challenge. Familiar phrases from other runs remain usable.

Phrase identity ignores case and surrounding whitespace for repeats, novelty, and matchup reuse, while the player's original wording is preserved for display. Synonyms and rewordings are not merged.

The game reuses database judgments per ordered challenge-and-answer matchup. A New matchup notice marks the first successful result for that matchup across the game. A familiar phrase can earn the notice against a new challenge if it wins; a newly judged loss and replaying a cached win never earn it. Shared judgment storage does not imply player accounts or a leaderboard.

Unfinished runs resume in the same browser after a refresh or return visit using browser-local storage. Design concepts must preserve continuity rather than force a fresh run on every visit.

The first rejecting verdict ends the run, including a cached rejection. Empty, over-limit, repeated, or digit-containing entries are blocked without ending the run; technical errors preserve progress and allow retrying. Digits `0–9` show the exact error `im bad at math` on submission. Existing saved verdicts keep their original wording. These are distinct states rather than alternate game-over messages.

Novelty is reserved for first-time winning matchups. Do not show a discovery notice on the loss state. This replaces the earlier phrase-based novelty decision at the user's explicit request.

### Design principles

- Outcomes use clear semantic schemes: accepted moves are green and rejected moves are red, with matching text/icon labels. Fresh, pending, and retry states remain neutral so technical failures are not confused with losing the game.
- The primary action is proposing what beats the current challenge.
- The goal is the longest accepted chain before losing.
- The interface should feel whimsical and playful.
- Fluid Functionalism is the requested component foundation.
- Responsive support must treat desktop and mobile as equally important, adapting the layout across viewports rather than shrinking one preferred version.
