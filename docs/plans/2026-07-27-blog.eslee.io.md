# Blog.eslee.io Implementation Plan

## Status

Approved following the design and architecture review on 2026-07-27.

## Goal

Add a standalone, typography-first technical blog at `blog.eslee.io`. The blog will be a Next.js application in the monorepo, use the existing Payload CMS and PostgreSQL database, and deploy independently to Vercel.

## Decision Map

```text
Blog launch
|- Platform
|  |- Standalone `apps/blog` application
|  |- Vercel deployment at `blog.eslee.io`
|  `- Payload Local API, following the Photography app pattern
|- Publishing
|  |- Long-form technical articles only
|  |- Payload drafts, versions, and scheduled publishing
|  |- Lexical editor with Markdown shortcuts and code blocks
|  |- Multiple authors per post; default the creator as an author
|  `- Reusable tags with generated slugs
|- Reader experience
|  |- Chronological archive with tag archive/filter routes
|  |- Article URLs at `/blog/[slug]`
|  |- Light and dark themes with a system-aware default and toggle
|  |- Typography-first articles; no cover images
|  |- Desktop-only generated table of contents
|  |- Syntax-highlighted code blocks with copy controls
|  |- Lightweight RSS feed, metadata, social cards, and sitemap
|  `- No comments, reactions, search, or draft-preview routes
`- Cross-site navigation
   |- Compact blog-header link to `eslee.io`
   `- `eslee.io` navigation link to `blog.eslee.io`
```

## Architecture

### Application and data access

1. Create `apps/blog` with the requested shadcn Next.js preset. Run the following command from the new, empty application directory:

   ```sh
   pnpm dlx shadcn@latest init --preset b3lX6r9Mo --template next
   ```

2. Integrate the generated application with the workspace conventions:

   - Name the package `@eslee/blog`.
   - Use `@eslee/tsconfig`, Tailwind v4, Biome, and the `@` source alias.
   - Add the same `with-env` command used by `apps/cms` and `apps/photography`; use port `3004` for local development.
   - Add `@eslee/payload`, `payload`, `@payloadcms/richtext-lexical`, and the minimal rendering dependencies required by the frontend.

3. Reuse the Photography app's direct Payload Local API approach in `apps/blog/src/server/payload.ts`:

   ```ts
   import { config } from "@eslee/payload";
   import { getPayload } from "payload";

   export const payload = await getPayload({ config });
   ```

   The public blog will use server-only query helpers rather than a browser-facing REST API. It will import Payload's generated types from `@eslee/payload` and keep database credentials exclusively on the server.

4. Add focused query helpers for the archive, tag archive, individual posts, sitemap, RSS, and metadata. Every public query must explicitly constrain results to `_status: "published"`, even though the CMS collection also enforces public published-only reads. This protects against accidentally rendering drafts because the Local API intentionally bypasses access control for its internal server calls.

5. Render current content at request time for the initial release. This keeps a newly published post live without a second cross-application revalidation endpoint or a secure preview workflow. Caching and Payload-triggered revalidation can be added later if traffic merits it.

### CMS model and access control

1. Extend `packages/payload/src/collections/Users.ts` with an author profile and editorial roles:

   - `role`: required select with `admin` and `author`, defaulting to `author`, included in the JWT.
   - `name`: required public display name.
   - `avatar`: optional relationship to `media`.
   - `bio`: optional short biography.
   - `website`: optional public URL.

   Existing CMS users will need a display name and role set in the admin UI before publishing posts. Keep authentication credentials and other private fields unavailable to public blog responses.

2. Add `packages/payload/src/collections/Tags.ts`:

   - `name`: required and unique display name.
   - `slug`: required, unique, indexed, generated from `name` when not supplied. For example, `Software Engineering` becomes `software-engineering`.
   - Public read access; create, update, and delete are restricted to authenticated administrators.
   - Configure the admin list to use the tag name as its title.

3. Add `packages/payload/src/collections/Posts.ts` with this editorial schema:

   - `title`: required title and source for the generated unique slug.
   - `slug`: unique, indexed URL segment; regenerate only when it has not been explicitly set.
   - `excerpt`: required plain-text summary used by archive cards, metadata, and RSS.
   - `content`: required Lexical rich text.
   - `authors`: required `hasMany` relationship to users.
   - `tags`: optional `hasMany` relationship to reusable tags.
   - `publishedAt`: set the first time a post becomes published and used for chronological ordering.
   - Payload draft/version support with autosave and scheduled publishing enabled.

4. Add a `beforeChange` hook for Posts. On create, if authors are absent, assign `req.user.id`. Preserve any explicit authors so an editor can create a co-authored post. The hook must not perform an unscoped nested Local API operation.

5. Apply least-privilege collection access:

   - Anonymous readers see only published posts and public tag information.
   - Authors can create posts and only read, update, or delete posts where they are listed as an author.
   - Administrators can manage every post, tag, and user profile.
   - Users can update their own public profile but cannot grant themselves an administrator role.

6. Update `packages/payload/src/payload.config.ts` to register Posts and Tags. Configure the shared Lexical editor for technical writing: headings beginning at `h2`, links, inline code, fenced code blocks with a language selector, inline media uploads, Markdown shortcuts/conversion, and the existing expected toolbars. Article titles own the document `h1`, so the content editor must not offer `h1`.

7. Export the new collection configs and generated `Post`, `Tag`, and author-facing types from `packages/payload/src/index.ts`.

### Public blog routes and UI

1. Build the root archive at `apps/blog/src/app/page.tsx`:

   - Reverse chronological list ordered by `publishedAt`.
   - Typography-led post rows with title, excerpt, date, co-author names, and tags.
   - No card art and no cover-image field.
   - Compact header with the blog label, a link to `https://eslee.io`, and the theme toggle.

2. Build article pages at `apps/blog/src/app/blog/[slug]/page.tsx`:

   - Resolve only published posts or return `notFound()`.
   - Render title, excerpt, publication date, author byline/profile links, and tags before the article body.
   - Render Lexical content through `@payloadcms/richtext-lexical/react` with application-owned JSX converters.
   - Add stable, deduplicated IDs to rendered headings and derive the table of contents from the same heading traversal.
   - Display the table of contents as a quiet sticky side rail only at desktop widths; omit it at narrower viewports and when there are too few headings.

3. Build tag archive pages at `apps/blog/src/app/tags/[slug]/page.tsx`. They share the chronological archive visual treatment but query only published posts related to the selected tag.

4. Add a server-rendered code-block converter:

   - Use language-aware highlighting that adapts to the active light or dark theme.
   - Preserve plaintext fallback for an unknown language.
   - Add a minimal client copy control that copies the original code, reports success accessibly, and does not force the article renderer to become a client component.

5. Use the shadcn preset as the foundation rather than adding a generic component gallery. Keep the visual language close to Vercel's editorial restraint: a narrow reading measure, deliberate type scale, strong code contrast, sparse rules, and no decorative media.

6. Add theme support with a system default and persistent toggle. Theme tokens must cover article typography, code syntax, metadata, focus states, and the table of contents in both modes.

7. Modify `apps/www/src/config/site.ts` to add the reciprocal `blog: "https://blog.eslee.io"` navigation link.

### Discovery and resilience

1. Generate page metadata from the post title and excerpt, including canonical URLs at `https://blog.eslee.io/blog/[slug]`.
2. Generate title-based Open Graph images. Do not add a per-post cover image solely for social sharing.
3. Add `app/sitemap.ts` for the archive, published article URLs, and tag archive URLs; add `app/robots.ts` permitting public crawling.
4. Add a lightweight `app/rss.xml/route.ts` that publishes title, excerpt, publication date, canonical URL, and authors. It intentionally does not serialize the full Lexical document in the initial release.
5. Include `not-found` and error UI that preserve the minimal visual language. Do not add comments, reactions, full-text search, analytics, newsletter capture, or preview URLs.

### Vercel deployment

1. Before deployment, synchronize Posts, Tags, and the User profile fields to the existing Payload database with the CMS's established schema workflow. Do not apply a newly generated baseline Payload migration to the live database: it would attempt to recreate the existing CMS tables. Create a true incremental migration or run the controlled schema push used for the current CMS deployment.
2. Create a Vercel project for `@eslee/blog` with `apps/blog` as its root directory.
3. Configure Vercel to install with PNPM and run the package build via Turborepo.
4. Set `DATABASE_URL` and `PAYLOAD_SECRET` in the project environments. The blog needs both because it follows the CMS's direct, type-safe Local API pattern. It does not require browser-exposed CMS credentials.
5. Assign `blog.eslee.io` to the Vercel project and add the DNS record Vercel provides.
6. Promote the existing CMS user to the `admin` role after the User role column exists, then complete its public author profile.
7. Verify production canonical URLs, sitemap, RSS, theme behavior, public published-only access, inline media, and cross-site links after the domain is active.

## Generated and verification work

1. Run `pnpm generate:types` after changing the Payload schema and update the generated types in the repository.
2. Run `pnpm generate:importmap` after Payload configuration changes that affect admin-rendered editor capabilities.
3. Add targeted tests for pure slug generation, public published-only query constraints, automatic author assignment behavior, and heading/TOC extraction.
4. Run `pnpm check:fix` after implementation.
5. Run `pnpm turbo run typecheck -F @eslee/payload -F @eslee/blog`.
6. Run `pnpm turbo run build -F @eslee/payload -F @eslee/blog`.
7. Manually verify the CMS workflow: create a draft, confirm creator defaulting and co-author selection, publish it, verify archive/tag/article/RSS/sitemap output, and confirm a draft never appears on the public blog.

## Deferred Work

- Secure public draft previews.
- On-demand revalidation from Payload after publishing.
- Search and analytics.
- Comments, reactions, subscriptions, or newsletters.
- Per-post cover images and author archive pages.
- Additional content formats beyond long-form articles.
